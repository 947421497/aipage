## 架构概述

### 设计理念

一鱼快速构架采用经典的 MVC（Model-View-Controller）架构模式，将应用程序分为模型层、视图层和控制器层三层结构。这种分层设计实现了数据处理、界面展示和业务逻辑的分离，提高了代码的可维护性和可复用性。框架追求简洁实用的设计理念，避免过度设计带来的复杂性，让开发者能够快速上手并高效开发。

### 核心组件

框架的核心由几个关键组件构成，它们相互协作完成请求处理的全过程。App 类是应用的入口和容器，负责初始化应用环境、加载配置、启动中间件、执行路由分发。Route 类负责 URL 解析和路由匹配，将用户请求映射到对应的控制器方法。Model 类封装了数据库操作，提供面向对象的 CRUD 接口。View 类负责模板解析和页面渲染，将数据与模板结合生成最终输出。

### 技术选型

在技术选型上，框架秉持稳定性和实用性并重的原则。PHP 版本要求 8.1 及以上，可以充分利用强类型、命名空间、Fiber 协程等现代特性。数据库层使用原生 PDO 封装，在提供便捷 API 的同时保持对 SQL 的完全控制。前端技术栈选择 Bootstrap 和 jQuery 作为基础，配合 Bootstrap Table 等组件库，能够快速构建功能完善的管理界面。

## 核心架构

### 应用架构

框架采用多应用架构设计，每个应用是独立的模块，拥有自己的控制器、模型、视图和配置。默认包含三个预置应用：admin（后台管理）、index（前台应用）、install（安装应用）。这种设计使得前台和后台代码完全隔离，便于独立开发和部署。应用之间可以通过命名空间调用实现代码共享，公共模型可以放在 app/common/model 目录下供各应用引用。

### 分层设计

#### 控制器层（Controller）

控制器是请求处理的调度中心，负责接收用户请求、协调模型处理、选择视图渲染。每个控制器对应一个资源或功能模块，如 User 控制器处理用户相关的所有操作。控制器的公共方法对应具体的 URL 操作，方法命名应简洁明确。控制器中应避免编写复杂业务逻辑，这些逻辑应该下沉到模型层处理。

#### 模型层（Model）

模型是数据访问层的抽象，封装了所有数据库操作。模型继承自框架的 Model 基类，自动获得增删改查等基础能力。模型中可以定义数据表名、主键名、时间戳字段、验证规则等元数据。复杂的查询逻辑和业务规则应该在模型中实现，保持控制器的简洁。

#### 视图层（View）

视图负责将数据渲染成用户可见的页面内容。视图使用模板引擎解析，支持变量输出、条件判断、循环遍历等语法。模板文件按控制器组织目录，如 User 控制器的视图放在 view/user/ 目录下。良好的视图设计应该关注用户体验，避免在视图中编写复杂逻辑。

## 请求生命周期

### 请求处理流程

整个请求处理流程从用户发送 HTTP 请求开始，到服务器返回响应结束。流程大致分为以下几个阶段：Web 服务器接收请求并根据配置决定是否重写到 index.php 入口文件；框架加载并初始化应用环境，包括定义常量、加载配置、注册自动加载等；执行全局中间件进行初始化处理；Route 类解析 URL 确定目标控制器和方法；执行应用级中间件进行权限验证等预处理；控制器方法执行，调用模型处理业务逻辑；视图渲染生成最终页面；响应返回给客户端。

### URL 解析规则

框架采用约定俗成的 URL 解析规则，URL 路径与控制器方法对应。默认情况下，URL 第一段为控制器名称（不含 Controller 后缀），第二段为方法名称，其余部分作为参数。例如，/admin/user/edit/id/5 解析为：应用 admin、控制器 user、方法 edit、参数 id=5。如果 URL 只包含一段，则作为控制器名称，默认方法为 index。

### 路由重写

为了美化 URL 并提升用户体验，框架支持 URL 重写功能。伪静态后缀默认配置为 .html，生成的 URL 通常带有此后缀。路由别名可以将复杂 URL 简化为语义化的别名。自动重写规则可以将特定格式的 URL 自动转换为框架期望的格式。这些配置在 config/route.php 文件中定义。

### 目录职责说明

app 目录是所有应用代码的存放位置，每个子目录代表一个独立应用。各应用下的 controller、model、view 子目录分别存放控制层、模型层、视图层代码，保持 MVC 结构清晰。config 目录集中管理所有配置文件，框架自动加载这些配置并注入到相应组件中。public 目录作为 Web 服务器根目录，禁止在此目录之外直接访问 PHP 文件，保障安全性。xphp 目录包含框架核心代码，开发者通常不需要修改此目录，仅在框架升级时需要更新。runtime 目录用于存储运行时生成的缓存、日志、会话等文件，此目录需要 Web 服务器有写入权限。

## 模块设计

### 后台管理模块

后台管理模块是系统的核心功能区，提供完整的管理界面。用户管理模块处理用户账号的增删改查、状态控制、等级调整等操作。菜单管理模块维护后台导航菜单，支持动态配置菜单项和权限控制。配置管理模块提供系统参数的在线编辑功能，无需修改代码即可调整系统行为。代码生成模块是框架的特色功能，可以根据数据表结构一键生成 CRUD 代码，大幅提升开发效率。

### 用户认证模块

用户认证模块处理用户的登录、退出和状态管理。前台认证使用 Auth 中间件，保护需要登录才能访问的页面。后台认证使用 CpAuth 中间件，验证管理员身份并检查权限等级。登录成功后创建会话，存储用户 ID 和基本信息。CSRF 防护中间件防止跨站请求伪造攻击，保护表单提交的安全性。

### 安装模块

安装模块负责系统初始化和数据准备。当检测到系统未安装时，自动跳转到安装页面引导用户完成配置。安装向导包括数据库配置、管理员账号创建等步骤。安装过程自动执行数据库迁移，创建所需的数据表并插入初始数据。安装完成后自动锁定安装功能，防止重复安装导致数据问题。

## 扩展机制

### 扩展架构

框架采用可扩展的架构设计，核心功能保持精简，常用功能以扩展形式提供。扩展类存放在 extend 目录，使用命名空间组织，可以像使用原生类一样方便地调用。扩展采用单一职责原则，每个扩展类只负责一个特定功能，如验证码、上传、邮件等。扩展之间无直接依赖，可以根据项目需求选择性加载使用。

### 内置扩展

Captcha 扩展提供验证码生成和验证功能，支持自定义字体、干扰线、背景等样式参数。Upload 扩展封装文件上传逻辑，支持图片、文档等多种类型，提供文件大小限制、类型验证等安全措施。Thumb 扩展用于生成图片缩略图，支持多种缩放模式和输出格式。Smtp 扩展封装邮件发送功能，支持 SMTP 认证和多种邮件格式。

### 扩展开发

开发者可以基于扩展机制开发自定义功能模块。扩展类应遵循命名规范，存放在 extend 目录下对应的子目录中。扩展类应该设计为可配置的，通过构造函数接收参数或使用配置数组。良好的扩展应该包含详细的使用文档和示例代码，便于其他开发者使用。

## 安全机制

### SQL注入防护

框架在数据库查询层内置 SQL 注入防护机制。所有用户输入的数据在进入查询前都会经过转义处理，确保特殊字符不会破坏 SQL 语句结构。推荐使用框架提供的查询构建器而非直接拼接 SQL 字符串，这样可以最大程度避免注入风险。如果必须使用原生 SQL，务必使用参数绑定而非字符串拼接。

### XSS防护

框架提供多种 XSS 防护手段。模板引擎默认会对输出变量进行 HTML 转义，防止恶意脚本注入。配置文件中可以设置是否启用自动转义，以及可信赖的 HTML 标签白名单。用户输入的数据在存储前通常不需要特殊处理，但在某些场景下可以使用 htmlspecialchars 函数进行额外转义。

### CSRF防护

Csrf 中间件提供跨站请求伪造防护功能。开启后，所有 POST、PUT、DELETE 请求都必须携带有效的 CSRF Token。Token 在表单页面自动生成，通过隐藏字段传递给服务器。框架会验证 Token 的有效性，拒绝无效或过期请求。这种机制可以有效防止第三方网站诱导用户执行非预期操作。

### 密码安全

用户密码使用双重 MD5 加密存储，加密时加入用户名作为盐值，增加破解难度。登录时使用相同的加密算法对比密码是否匹配。框架支持自定义密码加密方式，可以通过修改模型中的 getEncryptPassword 方法实现更安全的加密算法，如 bcrypt 或 argon2。
